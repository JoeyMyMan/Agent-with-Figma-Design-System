# ds-workflow playbooks

A workflow that keeps a Figma design system and code in sync. It works for any coding agent and for people: the rules are plain Markdown, the state is in files in the repo, and the gates are scripts. Each playbook covers one task and starts by saying when to use it. The `SKILL.md` in each folder can be loaded directly as an agent skill.

## Roles

- **Design system owner (designer)**: maintains the Figma library, approves or rejects proposals, publishes new versions, reviews the screens the project writes back, and marks sections as Ready for dev.
- **Project (you and your agent)**: consumer and proposer. Use only the tokens and components in the pinned version. If something is missing, propose it; do not invent it.

## Six principles

1. **Figma is the only source of tokens.** Tokens in code are generated by scripts. Code only references `var(--<prefix>-*)`, and the check blocks literals.
2. **One Figma component set maps to one code component.** Variant properties are the props. When writing back to Figma, screens consist only of component instances.
3. **Reuse first, then extend, and create new only as a last resort.** All three outcomes are recorded in the registry and marked the same way in Figma.
4. **Split variants by business dimension**: State, Selected, Validation, Size, and so on. Do not pack different meanings into one `Property 1`, and do not detach instances to fake variants.
5. **Everything is tied to a version.** `design-system/lock.json` pins the current version. Upgrades follow "sync → diff report → migrate → verify".
6. **The designer has the last word, in Figma.** Every UI change goes back to Figma for review; screens the designer marked Ready are never overwritten; state lives in the review ledger (`ds-review-loop`).

## Registry statuses

| Status | Meaning | In Figma |
| --- | --- | --- |
| `reuse` | Use the design system component as is | An instance of the original component |
| `extend` | Adds variants to an existing component set; awaiting approval | A copy on the proposal page, name suffixed "(EXTENDS <original component>)" |
| `proposed` | New component; awaiting approval | `<prefix>/<Area>/<Name>` on the proposal page (config `proposal.prefix`, default `Proposed`), description says Status: Proposed |
| `approved` | The designer has merged it into the library and published it | The official library component; the registry entry points to the new node id |
| `deprecated` | Retired; waiting for migration | — |

Components the designer creates after the pinned version go into the registry entry's `figmaPending` until the next sync. After the next `sync`, move them to `figma`.

## Required tools

- **Node ≥ 20**: `npx ds-workflow …`.
- **Figma MCP server** (official, from Figma): reads designs (`get_design_context`, `get_screenshot`, `get_metadata`) and runs scripts in a file (`use_figma`). Configure it and sign in from the agent you use.
- **Optional `FIGMA_TOKEN`**: needed only to sync through the REST API. Keep it in an environment variable, never in the repo. Variables require Enterprise `file_variables:read`; otherwise use the plugin export (ds-adopt).

## Working with different agents

The playbooks name the Figma MCP tools, not any agent's features. What differs between agents, and what to do:

| Capability | If the agent has it | If not |
| --- | --- | --- |
| Figma MCP read tools | Read designs and components directly | Ask a person for screenshots and the component's property list; do not guess from names |
| Figma MCP write (`use_figma`) | Proposals, write-back, review reminders | Finish the code, then hand the Figma steps to someone with write access (`ds-review-loop`) |
| Sub-agents / parallel tasks | Split mapping and implementation by area (`ds-map`, `ds-implement`) | Work area by area in sequence; keep the final completeness / diff review |
| Loading `SKILL.md` folders as skills | `npx ds-workflow rules --skills-dir <folder>` copies the playbooks there | Read the playbook from `docs/ds-workflow/` before the task (AGENTS.md lists them) |
| Memory across sessions | Optional | Not needed: everything that must persist is in the repo (lock, registry, ledger, proposals) |

Several agents (or agents and people) on one project: they share the files above and the gate, never each other's chat. Write the ledger and registry in the same commit as the change they describe.
